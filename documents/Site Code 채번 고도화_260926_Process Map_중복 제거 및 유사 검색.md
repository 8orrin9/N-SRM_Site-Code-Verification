# 중복 Site 식별 프로세스 (Deduplication)

표준화·실재검증을 마친 Site(업체) 정보에서 **동일 업체의 중복 행**을 자동 식별해
사용자에게 "중복 확정 / 중복 의심" 그룹으로 제시하기 위한 로직 명세다.
(실제 삭제는 사용자 판단이며, 본 로직은 **제시만** 한다.)

관련 모듈: `scripts/SIM_260926_dedup.py`
재사용 유틸: `SIM`(`STD_VLD_260917_std_company.py`), `haversine`(`STD_VLD_260917_geo_common.py`)

---

## 0. 대상 선정 / 예외처리

- **표준화 상태가 "실패"(`STATUS_FAILED`)인 행은 대상에서 제외**한다.
- 필드 결측(코드·Duns·좌표·addressComponents 없음)은 오류가 아니라 **해당 게이트만 스킵**한다.
  파이프라인 전체가 멈추지 않도록 각 게이트는 결측을 정상 흐름으로 처리한다.

---

## 1. 판정 게이트 (사용자 정의 1~6단계)

각 게이트는 두 행 `a`, `b`를 비교해 다음 넷 중 하나를 반환한다.

| 반환 | 의미 | 후속 처리 |
|---|---|---|
| `EQUAL` | 동일 | **중복 확정** → Union-Find 병합, 이후 게이트 불필요 |
| `SIMILAR` | 유사 | **중복 의심** 유지 → 다음 게이트로 |
| `DIFFERENT` | 다름 | **필터링** → 이 쌍은 비교 종료(중복 아님) |
| `SKIP` | 결측 | 이 게이트 판단 불가 → 다음 게이트로 |

> **핵심 원칙:** 기업식별코드와 Duns No.는 **완전히 별개의 독립 단계**다.
> 어느 하나가 결측이어도 즉시 판정 보류로 넘기지 않고, 결측인 그 게이트만 `SKIP`하고 다음 단계로 진행한다.

### 게이트 1 — 기업식별코드 (초엄격)
- 정규화(공백/구분자 제거) 후 **완전 일치** → `EQUAL` (중복 확정)
- 자릿수 동일 + 편집거리 ≤ 1 (오타 수준) → `SIMILAR` (의심)
- 그 외 → `DIFFERENT`
- 한쪽/양쪽 결측 → `SKIP`

### 게이트 2 — Duns No. (초엄격, 게이트 1과 독립)
- `-`/공백 제거 정규화 후 **완전 일치** → `EQUAL` (중복 확정)
- 자릿수 동일 + 편집거리 ≤ 1 → `SIMILAR` (의심)
- 그 외 → `DIFFERENT`
- 결측 → `SKIP`

> 게이트 1이 `SKIP`이어도 게이트 2는 독립적으로 판정한다. 반대도 마찬가지.

### 게이트 3 — 표준화 주소 (구조적)

구글 `addressComponents`를 사용한 **"계층 일치 + 하위만 토큰"** 방식이다.
표준화된 자유형 주소 문자열(`STD 주소`)을 통째로 비교하지 않고, 구글이 분해해 준
**구조화된 레벨**을 위계에 따라 단계별로 대조한다. 이렇게 하는 이유는 §3-5(설계 근거) 참조.

#### 3-1. 입력 정규화 — 레벨 맵 구성
각 행의 `addressComponents`(리스트)를 `{레벨: (long_norm, short_norm)}` 맵으로 접는다.

- 대상 레벨 위계(상위→하위):
  ```
  [상위 = 행정 경계]                 [하위 = 도로/번지]
  country                            route
  administrative_area_level_1        street_number
  administrative_area_level_2
  administrative_area_level_3
  locality
  sublocality
  ```
- 각 레벨은 **첫 번째로 등장한 컴포넌트 하나만** 채택한다(구글 응답은 상위 레벨을 중복 표기하기도 함).
- `long_norm`/`short_norm` = 해당 컴포넌트의 `long_text`/`short_text`를 소문자화 + 공백 정규화한 값.
  - `long_text`: 사람이 읽는 전체 표기(예: `"Seoul"`, `"서울특별시"`, `"대한민국"`).
  - `short_text`: 약어/코드 표기(예: `administrative_area_level_1`은 `"KR-11"`, `country`는 ISO `"KR"`).

#### 3-2. 비교 범위 — 공통 레벨만 (요구사항 4-1-1 / 4-2-1)
두 행이 **동시에 보유한 레벨**만 위계 순서대로 비교한다. 한쪽에만 있는 레벨(예: 한쪽은
`street_number`까지, 다른 쪽은 `locality`까지)은 **비교하지 않는다**. 정밀도가 낮은 쪽에 맞춰
"공통으로 확인 가능한 최하위 레벨까지만" 판정하는 것이 요구사항이다.

- 공통 레벨이 **하나도 없으면** → `SKIP` (판단 불가 → 좌표 게이트로).

#### 3-3. 레벨별 판정 규칙
공통 레벨을 하나씩 순회하며 다음을 적용한다.

**(a) 공통 선판정 — 모든 레벨 공통:**
두 값의 집합 `{long, short}`가 **교집합을 가지면 그 레벨은 "동일"** 로 보고 통과한다.
- `short_text`가 언어 독립 앵커(ISO 코드/행정 약어) 역할을 하므로 **다국어·약어 표기 차이를 흡수**한다.
- 예: `country`의 long이 `"대한민국"` vs `"Republic of Korea"`로 달라도 short가 둘 다 `"KR"` → 동일.
- 예: `locality`의 long이 `"서울"` vs `"Seoul"`이라도 short가 둘 다 `"Seoul"` → 동일.

**(b) 상위 레벨**(`country`~`sublocality`): (a)로 같지 않다면,
- `long` 정규화 **편집거리 ≤ `ADDR_UPPER_MAX_EDITS`(기본 1)** 인 **미세 오타만** 유사(`SIMILAR`)로 허용.
- 그 외에는 **다른 행정구역으로 간주해 즉시 `DIFFERENT`** (쌍 전체 비교 종료).
- 예: `"Gyeonggi"` vs `"Gyeonggj"`(1자 오타) → 유사. `"Jung-gu"` vs `"Jongno-gu"`(다른 구, 편집거리 큼) → `DIFFERENT`.

**(c) 하위 레벨**(`route`, `street_number`): (a)로 같지 않다면,
- `long`끼리, `short`끼리 각각 **토큰 Jaccard**를 계산해 **최댓값**이 `ADDR_LOWER_JACCARD`(기본 0.5)
  이상이면 유사(`SIMILAR`), 미만이면 `DIFFERENT`.
- 토큰 = 값을 공백 및 `, . / -` 로 분해한 조각들의 집합. Jaccard = `|교집합| / |합집합|`.
- 예: `route` `"26 Euljiro"` vs `"Euljiro 26"` → 토큰 `{26, euljiro}` 동일 → Jaccard 1.0 → 유사(순서 무관).
- `short` 병행 비교로 하위 레벨도 다국어 보정을 받는다.
  예: `"테헤란로"`(long) vs `"Teheran-ro"`(long)는 토큰이 안 겹치지만, short가 둘 다 `"teheran-ro"` → 동일.

#### 3-4. 레벨 종합 → 게이트 반환
| 공통 레벨 순회 결과 | 반환 |
|---|---|
| 모든 공통 레벨이 (a) 동일 통과 | `EQUAL` (중복 확정 근거) |
| 일부 레벨이 (b)/(c)에서 유사, 나머지는 동일, `DIFFERENT` 없음 | `SIMILAR` (중복 의심) |
| 어느 레벨이든 (b)/(c)에서 `DIFFERENT` | `DIFFERENT` (즉시 필터, 이후 게이트 불필요) |
| 공통 레벨 없음 | `SKIP` |

#### 3-5. 설계 근거 — 왜 업체명용 `SIM()`을 상위 레벨에 쓰지 않는가
초기 구현은 레벨 값을 업체명 유사도 함수 `SIM()`(JaroWinkler/token_sort/Levenshtein 최댓값, ≥0.85)에
그대로 통과시켰으나 두 가지 문제가 있었다.
1. **다른 행정구역 오탐:** `"Jung-gu"`↔`"Jongno-gu"`처럼 문자가 상당 부분 겹치는 **다른 구**가
   0.85를 넘겨 유사로 오인된다. 행정 경계는 "거의 같은 철자"만 같은 곳으로 봐야 안전하다.
2. **업체명 전용 정규화 오염:** `SIM()` 내부 `comparison_key`는 법인형태·업종 불용어(`co`, `ltd` 등)를
   제거하도록 설계돼 주소 토큰을 왜곡할 수 있다.

따라서 상위 레벨은 **short_text 교차 보정(언어 독립) + 초엄격 편집거리(≤1)** 로 판정하고,
문자 순서·표기 흔들림 허용이 실제로 필요한 **하위 레벨에만 토큰 Jaccard**를 적용한다.
(음역 문제 — 예: 상위 레벨의 `"서울"`↔`"Seoul"`처럼 언어 자체가 다른 경우 — 는 현재 short_text
앵커로 대부분 해소되며, 표준화 파이프라인이 일관된 `languageCode`로 지오코딩하므로 상위 레벨의
언어 혼재는 드물다. 잔여 케이스는 향후 음역 사전/`place_id` 앵커로 확장한다.)

### 게이트 4 — 좌표 거리 (Haversine)
- `haversine(coord_a, coord_b) ≤ COORD_EQUAL_M`(기본 100m)
  → 주소 레벨이 서로 달라도 **동일 업체로 빠르게 확정** (`EQUAL`, 요구사항 5-1-1 취지)
- 초과 → `DIFFERENT`
- 좌표 결측 → `SKIP`

### 게이트 5 — 표준화 업체명 (최종 확인, `SIM` 재사용)
앞 단계에서 확정/의심으로 살아남은 쌍에 대해 **반드시** 최종 교차 확인한다.
- `SIM(std_name_a, std_name_b)`의 `is_match`(≥ 0.85) → 유지
- 미달 → `DIFFERENT` (동명이 아닌 다른 업체로 간주, 필터링)
- **확정 경로:** 업체명이 결측(`SKIP`)이면 코드/좌표 등 강한 근거로 확정 유지.
- **의심 경로:** 유사 신호는 약한 근거이므로 업체명이 `EQUAL`로 **뒷받침될 때만** 의심으로 남긴다.
  업체명이 다르거나 결측이면 필터링한다. (같은 도시에 있는 무관한 업체들이 의심으로 폭증하는 것을 방지)

## 2. 게이트 실행 순서와 판정 종합

한 후보 쌍에 대한 판정 흐름:

```
표준화 실패 행?  ── 예 ─▶ 대상 제외
        │ 아니오
        ▼
게이트1(코드)  ─ EQUAL ─────────────────┐
        │ SIMILAR / SKIP                 │
        ▼                                │
게이트2(Duns)  ─ EQUAL ─────────────────┤
        │ SIMILAR / SKIP                 │  (확정 후보)
        ▼                                │
게이트3(주소)  ─ EQUAL ─────────────────┤
        │ SIMILAR / SKIP                 │
        ▼                                │
게이트4(좌표)  ─ EQUAL ─────────────────┤
        │ SKIP                           │
        ▼                                ▼
   (확정 근거 없음)              게이트5(업체명 SIM)
        │                          │ is_match?
        │                    ┌─────┴─────┐
        ▼                   예           아니오
   의심 이력 있으면          ▼             ▼
   → 중복 의심          중복 확정      필터링(중복 아님)
   없으면 → 필터링       (union)
```

- 어느 게이트든 `DIFFERENT`가 나오면 즉시 그 쌍은 **필터링**(중복 아님)으로 종료한다.
- `EQUAL`로 확정 근거가 생기면 **게이트 5(업체명)로 교차 확인** 후 최종 확정한다.
  (코드/Duns/주소/좌표가 같아도 업체명이 전혀 다르면 데이터 오류일 수 있으므로 최종 방어.)
- 확정 근거 없이 `SIMILAR`만 쌓이면 **중복 의심**으로 분류한다.

## 3. 효율화 — 블로킹(Blocking) + Union-Find

### 왜 필요한가
모든 쌍을 비교하면 O(n²)라 대규모 데이터에서 감당 불가하다
(1만 행 → 약 5천만 쌍). 또한 이미 비교/확정된 쌍을 다시 비교하는 낭비를 막아야 한다.

### 블로킹 — "비교할 후보 쌍만 추린다"
값싼 **블록 키**로 후보 그룹을 만들고, **같은 블록 안에서만** 상세 게이트를 돌린다.

| 블록 키 | 생성 조건 | 대응 게이트 |
|---|---|---|
| `code:<정규화 코드>` | 기업식별코드 있음 | 1 |
| `duns:<정규화 Duns>` | Duns 있음 | 2 |
| `geo:<위·경도 그리드 셀>` | 좌표 있음 | 4 (근접) |
| `addr:<공통 상위 지명(locality 등)>` | addressComponents 있음 | 3 |
| `name:<업체명 정규화 키>` | 업체명 있음 | 5 |

- `name` 키는 코드·Duns가 **결측이거나 오타(유사)** 라 코드 블록을 공유하지 못하는
  동명 후보를 놓치지 않기 위한 안전망이다(최종 게이트가 업체명이므로 정합적).
- 어떤 블록도 공유하지 않는 두 행은 **애초에 비교하지 않는다.**
- 좌표 그리드 셀은 인접 셀 경계 문제를 줄이기 위해 반올림 셀 + 이웃 셀까지 포함할 수 있다(구현 시 조정).

### Union-Find — "확정 중복을 클러스터로 병합 + 재비교 차단"
- 확정 쌍마다 `union(i, j)`.
- **전이성:** A=B, B=C를 확정하면 A·C를 직접 비교하지 않아도 한 클러스터가 된다
  (`find(A) == find(C)`).
- **재비교 방지:** 두 행이 이미 같은 클러스터면(`find(i) == find(j)`) 게이트를 다시 돌리지 않고 건너뛴다.
- **중복 등장 쌍 1회 처리:** 여러 블록에 동시에 걸린 쌍은 `seen_pairs` 집합으로 한 번만 판정한다.

### 재비교 방지 3중 메커니즘 (사용자 우려 사항)
1. **블록 키**: 후보 쌍 자체를 줄인다(관련 없는 쌍은 생성 안 함).
2. **`seen_pairs`**: 서로 다른 블록에서 같은 `(i, j)`가 나와도 판정은 1회.
3. **`find(i) == find(j)`**: 이미 같은 클러스터로 확정된 쌍은 게이트 재실행 없이 스킵.

## 4. 산출물 형태 (클러스터 단위)

`dedup(rows)` 반환:

```python
{
  "clusters": [           # 중복 확정 그룹 (2개 이상 행)
    {
      "member_indices": [2, 5, 8],
      "representative": 2,           # 대표 행(예: 가장 낮은 인덱스)
      "reasons": ["code", "addr", "coord"],  # 확정에 기여한 게이트
    },
    ...
  ],
  "suspects": [           # 중복 의심 엣지 (확정 아님)
    {"pair": [3, 11], "reason": "duns_similar", "name_score": 0.88},
    ...
  ],
}
```

- 단일 행(중복 없음)은 clusters에 포함하지 않는다.
- 의심 엣지는 union하지 않고 별도로 남겨 사용자 검토에 맡긴다.

## 5. 임계값 (튜닝 가능, 모듈 상수로 노출)

| 상수 | 기본값 | 의미 |
|---|---|---|
| `CODE_SIMILAR_MAX_EDITS` | 1 | 코드/Duns 유사 판정 최대 편집거리(초엄격) |
| `COORD_EQUAL_M` | 100.0 | 좌표 동일 판정 거리(m) |
| `GEO_GRID_DECIMALS` | 2 | 좌표 블록 그리드 반올림 자릿수(≈1km) |
| `ADDR_UPPER_MAX_EDITS` | 1 | 주소 상위 레벨(행정구역) 오타 허용 최대 편집거리(초엄격) |
| `ADDR_LOWER_JACCARD` | 0.5 | 주소 하위 레벨(도로/번지) 토큰 Jaccard 유사 임계 |
| `SIM_THRESHOLD`(재사용) | 0.85 | 업체명 최종 확인 임계 |

임계값은 Golden Dataset으로 실측 후 조정한다.

# 유사 Site 검색 프로세스 (Similarity Search)

신규 입력(쿼리) Site가 **이미 채번된 기준(reference) Site 집합**에 존재하는지 확인하기
위한 로직 명세다. 존재하면 기존 Site Code를 재사용하고, 없으면 **신규 채번 후보**로
제시한다. 실제 채번/재사용 결정은 사용자 판단이며, 본 로직은 **유사 후보를 점수와 함께 제시만** 한다.

관련 모듈: `app/backend/find_similar.py` (신규 얇은 래퍼)
재사용(수정 금지, 호출만): 중복 제거의 게이트 `code_gate`/`duns_gate`/`address_gate`/`coord_gate`/
`name_gate`와 변환기 `_to_rows`(`SIM_260926_dedup.py`), `SIM`(`STD_VLD_260917_std_company.py`),
`haversine`(`STD_VLD_260917_geo_common.py`)

> **핵심 설계:** 유사 검색은 중복 제거와 **동일한 단계적 게이트**를 그대로 재사용한다. 다만 결과를
> "확정/의심/무관"으로 **분류**하지 않고, 각 게이트의 **EQUAL 근접도를 가중치**로 삼아 업체명 SIM
> 점수와 결합해 **하나의 종합 순위 점수**로 환산한다. 즉 "같으면 자른다(gate)"는 판정 로직을
> 그대로 쓰되, 출력만 "얼마나 닮았나 줄 세운다(rank)"로 바꾼 것이다.

---

## 1. 입력 / 출력

- **입력:** `query_rows`(확인할 신규 Site 행들), `reference_rows`(기준 Site 행들), `top_k`(기본 8).
- **비교 단위:** 각 쿼리 행 × 모든 기준 행 (전수 1:1). 블로킹은 적용하지 않는다(§6 참조).
- **정규화 일관성:** 쿼리·기준 행을 `_to_rows([row])[0]`로 게이트 입력 형식
  (`{code, duns, std_name, coord, components}`)으로 변환한 뒤 게이트에 넘긴다. 중복 제거와
  동일한 정규화(코드/Duns 영숫자화, 주소 `addressComponents` 구조 비교, 좌표 haversine)를 공유한다.
- **출력** (`search(query_rows, reference_rows, top_k)` 반환):

```python
[
  {
    "query_index": 0,
    "matches": [                         # avg(종합 순위 점수) 내림차순, 상위 top_k건
      {"ref_index": 5, "ref_row": {...},
       "nameSim": 92, "corpSim": 100, "dunsSim": null,   # SKIP은 null(정보없음)
       "addrSim": 60, "coordSim": 88, "avg": 100,
       "gates": {"code":"EQUAL","duns":"SKIP","addr":"SIMILAR","coord":"EQUAL","name":"EQUAL"},
       "vetoed": false},
      ...
    ]
  },
  ...
]
```

- 종합 점수(`avg`)는 **0~100 정수**. 필드 서브점수는 0~100 정수 또는 **`null`(SKIP=정보없음)**.
- `matches`는 `avg` 내림차순 정렬 후 상위 `top_k`건만 남긴다.

## 2. 게이트 판정 → EQUAL 근접도

각 게이트(코드/Duns/주소/좌표)는 중복 제거와 동일하게 `EQUAL/SIMILAR/DIFFERENT/SKIP` 중 하나를
반환한다(판정 규칙은 이 문서 앞부분 §게이트 1~4 참조). 이를 **근접도 `c`** 로 환산한다.

| 판정 | 근접도 `c` | 의미 | 필터 효과 |
|---|---|---|---|
| `EQUAL` | 1.0 | 정규화 후 동일 | 강한 양의 신호 |
| `SIMILAR` | 0.6 | 미세 오타/토큰 부분일치 | 약한 양의 신호 |
| `DIFFERENT` | 0.0 | 적극적 모순 | 필터 신호(§4) |
| `SKIP` | — | 정보 없음(결측) | **집계 분모에서 제외**(0점 아님) |

> **`SKIP`은 0이 아니다.** "정보 없음"을 0점으로 처리하면 "모순(DIFFERENT)"과 구분되지 않아,
> 결측이 흔한 데이터에서 강한 단일 신호(예: Duns만 일치)가 부당하게 눌린다. 그래서 SKIP은
> 점수 집계의 **분모에서 아예 제외**하고, 화면에는 빨간 0이 아니라 "—"로 표시한다.

### 2-1. 코드/Duns 게이트 완화 — 자릿수 조건 제거(래퍼에서 재분류)

중복 제거의 코어 게이트(`_code_like_gate`)는 유사(`SIMILAR`) 판정 시 **`len(a)==len(b)`(자릿수 동일)**
조건을 요구한다. 이 때문에 **숫자 1개 삽입·삭제 오타**(예: `56789`↔`5678`, 편집거리 1)가
`DIFFERENT`로 떨어져, 유사 검색에서 진짜 후보에 부당한 veto가 걸리고 순위에서 누락되는 문제가 있었다.

유사 검색은 "검색/제시" 목적이므로, `find_similar.py`의 래퍼(`_relax_id_gate`)에서 코드/Duns
게이트를 **후처리 재분류**한다(코어는 수정하지 않음):

- 게이트가 `DIFFERENT`라도 **정규화 값의 편집거리 ≤ `CODE_SIMILAR_MAX_EDITS`(기본 1)** 이면
  자릿수 차이와 무관하게 `SIMILAR`로 본다 → veto 미발동, 근접도 0.6 기여.
- 편집거리가 크면(예: `AAA111`↔`BBB222`) 그대로 `DIFFERENT` 유지 → veto.

> 예: 쿼리 Duns `56789`, 기준 Test_1의 Duns `5678`은 편집거리 1(삽입 오타)이라 `SIMILAR`.
> 완화 전에는 `DIFFERENT`→veto ×0.35로 33점(25위)까지 밀렸으나, 완화 후 93점(1위)으로 복귀한다.

## 3. 종합 순위 점수 공식 (`score_pair`)

가중치(모듈 상수, 튜닝 가능): `W_duns=0.35, W_code=0.30, W_coord=0.20, W_addr=0.15`.
`nameSim = SIM(std_name_q, std_name_ref)[0]` (0~1, 업체명 결측이면 N=None).

```
# A. 게이트 근거 G — SKIP 아닌 게이트만 분모에 포함
present = {g : verdict_g ≠ SKIP}
G = Σ_{g∈present} W_g·c_g / Σ_{g∈present} W_g        # present 비면 G=None

# B. 업체명 항 (약한 유사 감쇄)
N = nameSim                                          # 결측이면 None
if N is not None and 업체명==DIFFERENT:              # SIM<임계(0.85) — 우연히 겹치는 약한 유사
    N = N · WEAK_NAME_FACTOR(=0.6)                   # 결합 기여만 감쇄(표시용 nameSim은 원점수 유지)

# C. 강신호 dominance
G_strong = 1.0   if 코드==EQUAL or Duns==EQUAL       # 식별자 완전일치는 그 자체로 확정적
         = 0.85  if 주소==EQUAL or 좌표==EQUAL
         = 0.0   otherwise

# D. 결합 (evidence-dominant max-blend)
if G is None and N is None: base = 0
elif G is None:             base = N
elif N is None:             base = G
else:                       base = max(0.6·G + 0.4·N, G_strong, N)

# E. 식별자 충돌 veto + 0~100 스케일
V = 0.35  if 코드==DIFFERENT or Duns==DIFFERENT       # 아래로 가라앉되 목록엔 남김
  = 1.0   otherwise
avg = round(100 · V · base)
```

`max(…, G_strong, N)` 항이 **강한 단일 신호(Duns EQUAL 등)가 나머지 결측에도 지배**하도록 만든다.
이것이 옛 단순 평균(÷5)의 핵심 결함 — 강신호 희석 — 을 제거하는 장치다.

**약한 이름 감쇄(B항):** 업체명 SIM이 매칭 임계(0.85) 미만이면 게이트는 `DIFFERENT`로 본다.
이때 원점수 그대로 `N`에 반영하면 `test`↔`LT Metal Co`(SIM 0.73)처럼 **우연히 문자가 겹치는
무관한 업체**가 상위권을 잠식한다(짧은 쿼리일수록 심함). 그래서 이름 게이트가 `DIFFERENT`면
결합용 `N`만 `WEAK_NAME_FACTOR(=0.6)`으로 감쇄한다(표시용 `nameSim`은 원점수 유지 — 투명성).
예: `test`↔`LT Metal Co`는 avg 73(1위)→44로 내려가고, 이름·좌표·Duns가 실제로 맞는 진짜 후보가
상위로 올라온다.

## 4. 필터 규칙 — 소프트 필터 + 식별자 충돌 veto

결과가 **랭킹**이므로 후보를 목록에서 완전히 제거하지 않고, 강도별로 **감점**한다.

- **코드 OR Duns == DIFFERENT** → **식별자 충돌**로 간주해 강한 곱셈 패널티 `V=0.35`.
  서로 다른 등록 식별자는 다른 법인일 가능성이 높다. 다만 OCR/오타로 인한 오판 여지가 있어
  **완전 배제 대신 하위로 가라앉히고**, 화면에 `식별자 충돌` 뱃지로 표시해 사람이 확인하게 한다.
- **주소 OR 좌표 == DIFFERENT** → **soft**: 근접도 0 기여만, veto 없음.
  (지사/HQ/공장 등 동일 업체의 위치 차이는 흔하므로 좌표·주소 불일치를 강하게 처벌하지 않는다.)
- **SKIP**은 어디서든 중립 — 감점 없음.

> **판단(트레이드오프):** 중복 제거의 `classify_pair`는 어느 게이트든 DIFFERENT면 즉시 NONE(배제)이다.
> 유사 검색은 "검색/제시" 목적이라 dirty data 한 자리 차이로 동명 실업체를 **말없이 누락**시키는 것이
> 더 나쁜 UX라고 보아, 배제 대신 감점 후 하위 노출로 설계했다(사용자 확정). 최종 컷은 §5 임계로 한다.

---

## 5. 매칭 판정 — "신규 채번 / 코드 매핑 기준 점수"

랭킹된 후보 중 **최고 후보(matches[0])의 avg**를 사용자 조절 컷오프와 비교한다.
프론트엔드 슬라이더 **"신규 채번 / 코드 매핑 기준 점수"**(0~100, 기본 60)가 이 컷오프다.

- `matches[0].avg ≥ 기준 점수` → **기존 코드 매핑**(기존 Site로 간주, Site Code 재사용).
- `matches[0].avg < 기준 점수` → **신규 채번 후보**.

결과 요약 테이블의 맨 끝 **판정** 열에 이 결론을 배지로 명시한다 —
`코드 매핑`(파란 배지) 또는 `신규 채번`(노란 배지). 슬라이더를 움직이면 즉시 재판정되어
어떤 후보가 매핑/신규로 갈리는지 사용자가 바로 확인할 수 있다.

백엔드는 임계와 무관하게 항상 상위 `top_k`를 반환하고, **매칭/신규 판정은 프론트에서** 수행한다
(백엔드 무상태). `avg`가 이제 결측-인지·veto-반영 종합 점수라 같은 기본값(60)이 훨씬 유의미하다.
(슬라이더 세부 튜닝은 이 스코어링 안정화 후 재논의.)
